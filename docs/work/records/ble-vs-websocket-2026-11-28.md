# BLE と WebSocket の手指フレーム経路の計測（2026-11-28）

Issue #17（親 #3）の PoC で、Android から PC へ手指フレームを送り、BLE と WebSocket（LAN / USB）の帯域・遅延・欠落を同じ方法で測った記録。生データは [`ble-vs-websocket-2026-11-28/`](./ble-vs-websocket-2026-11-28/) にある。

## 結論

- **BLE は、仕様案のバイナリ形式（1 手 148 B、2 手 278 B）なら 2 手 60 fps まで欠落 0 で届いた。** 接続間隔 15 ms のとき、RTT の中央値は約 30 ms、P95 は 33〜44 ms。受信間隔は接続間隔（15 ms）の倍数に揃う。
- **BLE に今の JSON（1 手約 2 KB、2 手約 2.9 KB）を載せるのは不可。** 1 手 20 fps でも RTT の P95 が 189 ms に悪化し、1 手 30 fps 以上では送信がリンクの容量（実測で約 60〜68 kB/s）に迫って、制御の往復が数百 ms〜数秒詰まった。2 手 30 fps では、送信をやめた後も約 10 秒分のフレームが届き続けた。
- **接続間隔は PC（central）が決める。** Windows の既定（要求なし）では 60 ms になり、バイナリ 2 手 30 fps でも RTT の中央値が 117 ms になった。BLE を使うなら、PC 側で ThroughputOptimized（15 ms）を要求することが前提になる。
- **WebSocket（LAN）は RTT の中央値が約 5 ms と最も速いが、揺れが大きい。** バイナリのような小さいフレームでは RTT の P95 が 82〜106 ms、受信間隔の P95 が約 110 ms になった。JSON のように送信量が多い条件では P95 が 5〜34 ms に収まった。
- **WebSocket（USB、adb reverse）は参考値。** RTT の中央値が約 4.5 ms、P95 が 6〜14 ms で、今回の経路の中で最も安定している。

### 採否の推奨（判断待ち）

**同じ LAN が使えないときの代替経路として BLE を採用し、手指フレームはバイナリ形式に限る**ことを推奨する。理由は次のとおり。

1. LAN が無い状態でも、2 手 30 fps のバイナリを欠落 0、RTT P95 45 ms 以下で届けられた。今の目標（20〜30 fps、2 手）に足りる。
2. LAN の WebSocket は中央値こそ BLE より速いが、Wi-Fi 側の揺れで P95 が約 100 ms になる条件があり、遅延の上限では BLE と大差ない（同じ LAN が前提である点も変わらない）。
3. JSON は BLE の容量を超えるため、BLE を採るならバイナリ形式（PR #44 の仕様案）の採用が前提になる。

採る場合の条件:

- PC 側で接続パラメータ（ThroughputOptimized など）を要求する。要求しないと接続間隔が 60 ms になる。
- 送信側の「最新優先」は、Android の通知キューの外側では効かない（後述）。送る量を BLE の容量より十分小さく保ち、可能なら PC からの受信確認で送信を絞る。
- 本番に組み込む前に、Desktop（Flutter / Windows ネイティブ）側の受け口、ペアリングと再接続の手順、他 OS（macOS / iOS）の制約を確かめる。

## 方法

- Android 側は計測専用の `bench/TransportBenchActivity`（adb から起動）で、合成した手指フレームを指定の fps で生成して送る。カメラと MediaPipe は使わない。手順とプロトコルは [`android/tools/ble-bench/README.md`](../../../android/tools/ble-bench/README.md)。
- フレームの中身:
  - `bin`: 仕様案（`docs/system/binary-hand-frame-draft.md`、PR #44）のバイナリ。z と source あり。1 手 148 B、2 手 278 B。
  - `json`: 本番と同じ JSON `hand_frame`（互換用 `hand` と `source` つき）。1 手約 2,057 B、2 手約 2,941 B。
- BLE: Android が peripheral（GATT サーバ + advertising）、PC が central。手指フレームは FRAME characteristic の notify、制御（PING / START / STOP）は CONTROL characteristic への write with response、応答は CONTROL の notify。1 回の通知は min(MTU − 3, 512) B までで、超えたら 7 B のヘッダを付けて分割する。
- WebSocket: PC が待ち受け、Android（OkHttp）が接続する。バイナリはバイナリフレーム、JSON は本番と同じ文字列フレーム。
  - `ws-lan`: スマホ（Wi-Fi）から PC の LAN アドレスへ接続。Windows ファイアウォールの設定は変えずに受信できた。
  - `ws-usb`: `adb reverse tcp:8765 tcp:8765` を通して USB で接続。**LAN ではなく USB 経由の下限の目安**で、実運用の経路ではない。
- 時刻はすべて PC の単一の単調時計（`time.perf_counter_ns`）で測った。端末をまたいだ時計の引き算はしていない。
  - RTT: フレーム送信中に 200 ms ごとに PC → Android の PING を送り、PONG を受けるまで。BLE では write with response の完了待ちを含む。
  - 受信間隔: フレームが揃った（分割なら最後の断片が届いた）時刻の差。
  - 実効帯域: 受信したフレームのバイト数の合計 ÷ 最初から最後の受信までの時間。
  - 未着: 「生成したフレームのうち届かなかった割合」と「1〜最大受信 frameId のうち届かなかった数」。後者には Android 側で送信待ちが上書きされた数（上書き）を含む。
- 各条件 30 秒。条件は 1 手 / 2 手 × 20 / 30 / 60 fps（bin）と、JSON の 1 手 20 fps・1 手 30 fps・2 手 30 fps。

## 考察

### BLE の MTU・分割・接続間隔

- Windows（central）は接続直後に MTU 517 を取り決めた。Android（peripheral）からは MTU を要求できない（要求は central の API）。
- ATT の上限は MTU − 3 = 514 B だが、**Android は 1 回の通知を 512 B までに制限している**。最初のビルド（`d871b9e`）は 514 B で送ろうとして JSON の分割送信がすべて例外になり、`416c24f` で分割単位を min(MTU − 3, 512) に直した。
- バイナリは 2 手 278 B でも 1 回の通知に収まり、分割は要らなかった。既定 MTU 23 のままの相手では 278 B が 17 分割になるため、MTU を広げられない組み合わせでは使えない見込み（未計測）。
- 接続間隔は PC 側が決める。ThroughputOptimized を要求すると 15 ms（peripheral latency 0、supervision timeout 2 s）、要求しないと 60 ms（同 9.6 s）だった。Android 側の `requestConnectionPriority` は GATT クライアントの API なので、peripheral の今回の構成では使っていない。
- BLE の受信間隔は接続イベントの間隔（15 ms）の倍数になる。20 fps（50 ms）は 45 ms と 60 ms が交互に現れ、P95 が 60 ms になる。RTT の約 30 ms は接続イベント 2 回分（PING の書き込みと PONG の通知）にあたる。

### BLE の容量と「最新優先」が効かない問題

- 15 ms の接続間隔で実際に流れた量は最大約 68 kB/s（2 手 JSON）。JSON 1 手 30 fps（約 62 kB/s）でほぼ容量に達し、2 手 30 fps（約 88 kB/s）は容量を超えた。
- 容量を超えると、フレームは Android の Bluetooth スタック内で溜まり、遅れて届く。2 手 JSON 30 fps では STOP の後も 9.9 秒、既定の接続間隔の 1 手 JSON 20 fps では 17.5 秒、フレームが届き続けた。
- Android の `onNotificationSent` は無線で送り終えた時点ではなく、スタックが受け付けた時点で返る（推測。上の溜まり方と合う）。そのため送信側で「1 枠だけ持ち、新しいフレームで上書きする」最新優先を組んでも、スタックの手前でしか効かず、遅延の増加を防げなかった。実際、上書きはほとんど起きていない（2 手 JSON でも 977 件中 7 件）。
- PC → Android の制御（write with response）も同じリンクを使うため、容量に近づくと PING の往復が数百 ms〜10 秒詰まった。手指フレームが多いときは、制御の到達も遅れる。

### WebSocket（LAN）の揺れ

- 小さいフレーム（bin）では RTT の P95 が約 100 ms、受信間隔の P95 が約 110 ms で、60 fps では複数のフレームがまとめて届いた（間隔 P50 が 0.01 ms）。送信量の多い JSON の条件では P95 が 5〜36 ms に収まった。
- 約 100 ms という値は Wi-Fi のビーコン間隔（102.4 ms）に近く、送信量が少ないときにスマホの Wi-Fi が省電力状態に入っている可能性がある（推測。端末側の設定やアクセスポイントは調べていない）。計測前の ICMP ping が 50〜146 ms と揺れていたこととも合う。
- 本番の JSON 送信は送信量が多い側に入るため、本番の挙動は JSON の行に近いと考えられる。ただし、バイナリ化で送信量を減らすと、LAN では揺れが増える可能性がある。

### USB（adb reverse）

- RTT の中央値約 4.5 ms は経路の下限の目安。BLE の中央値（約 30 ms）との差は、主に BLE の接続間隔による。
- 30 / 60 fps で受信間隔の P95 が約 44 ms になるのは、Android 側で生成タイマーや送信スレッドが時々遅れるためと考えられる（推測）。BLE と LAN の値にも同じ揺れが含まれている。

## 実機で起きた問題

- **514 B の通知が送れない**: 上記のとおり。`416c24f` で修正し、計測はすべて修正後のビルドでやり直した。
- **切断直後の再接続が 1 回失敗した**: 5 秒のスモーク計測で切断した 1 分ほど後に接続しようとしたところ、advertising は見つかったが接続が 30 秒でタイムアウトした。Activity を開き直すと接続できた。別の機会には、開き直さずに再接続できた。原因は分かっていない。各計測の前には Activity を開き直した。
- **容量超過で切断した**: 修正後の最初の計測で、JSON 2 手 30 fps の最中に PC からの書き込みが `Unreachable` になり、接続が切れた（その後の計測のやり直しでは切れなかった）。BLE で容量を超えて送り続けると、遅延だけでなく切断も起こりうる。
- PC 側の計測ツールは、制御の書き込みが詰まると条件の時間が指定の 30 秒より延びる（`run_s` 列。最大 32.6 秒）。

## 未実施・残っていること

- 逆の役割（Windows を peripheral、Android を central）と、macOS / iOS の制約の調査。
- Desktop（Flutter / Windows ネイティブ）での BLE の受け口。今回の受信側は Python（bleak）の計測ツールで、Desktop アプリには繋いでいない。
- ペアリング（暗号化）ありの接続。今回は暗号化なしの GATT。
- 既定 MTU 23 の相手（分割が要る場合）、2M PHY が使えない相手での計測。
- 実際のカメラ・MediaPipe と同時に動かしたときの影響（CPU 負荷、カメラとの干渉）と、電池消費。
- 長時間（30 分以上）の安定性、離れた距離や遮蔽物がある場合、Wi-Fi（2.4 GHz）と同時に使った場合の干渉。
- BLE の受信確認による送信の絞り込み（フロー制御）の試作。
- WebSocket（LAN）の揺れの原因の切り分け（スマホの Wi-Fi 省電力の設定、5 GHz / 2.4 GHz、アクセスポイント）。

## 生データ

[`ble-vs-websocket-2026-11-28/`](./ble-vs-websocket-2026-11-28/) に、経路ごとに 3 つの CSV がある（`ble`、`ble-defaultparams`、`ws-lan`、`ws-usb`）。

- `<経路>-summary.csv`: 条件ごとの集計（上の表の元。Android 側の送信カウンタ、MTU、接続間隔を含む）。
- `<経路>-frames.csv`: フレームごとの到着時刻（START からの ms）、バイト数、分割数。
- `<経路>-rtt.csv`: PING ごとの RTT。
